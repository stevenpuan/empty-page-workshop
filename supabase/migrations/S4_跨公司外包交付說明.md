## 1. 後端交付物

### 008_cross_company.sql 包含：

| # | 物件 | 說明 |
|---|------|------|
| 1 | `vendors` 擴充 3 欄 | `linked_company_id`、`auto_dispatch`、`partner_routing_template_id` |
| 2 | `cross_company_links` 表 | 跨公司外包橋接表，一筆 link = 祥興一道外包工序 ↔ 沂融一張工單 |
| 3 | `cross_company_events` 表 | 每一次跨公司動作的完整日誌 |
| 4 | `payables` 基礎表 | 應付帳款（S5 將擴充觸發器與付款沖帳） |
| 5 | `receivables` 基礎表 | 應收帳款（S5 將擴充） |
| 6 | RLS 政策 | links 雙方可讀、manager 可寫；events 雙方可讀；payables/receivables 本公司 manager 可讀寫 |
| 7 | `outsource_stats` view | 外包統計摘要（各狀態計數、逾期、金額） |
| 8 | `group_reconciliation` view | 集團往來對帳（含金額不一致偵測） |
| 9 | `dispatch_outsource` RPC | 核心發包流程（11 步驟，security definer） |
| 10 | `complete_outsource` RPC | 對方完工回寫（產生應付+應收，security definer） |
| 11 | `reject_outsource` RPC | 沂融拒接（退回發包方工序，security definer） |
| 12 | `cancel_outsource` RPC | 祥興取消發包（security definer） |
| 13 | `trg_z_auto_complete_outsource` trigger | 沂融最後工序 done 時自動呼叫 complete_outsource |
| 14 | 模組權限種子 | outsource（老闆/店長 讀寫、員工 唯讀）、group_overview（老闆 讀寫） |
| 15 | doc_no_counters 種子 | AP / AR 類型兩家公司各一筆 |

### dispatch_outsource 流程（11 步）

```
① 驗證呼叫者是 manager/owner
② 取得並驗證工序（須為 pending/assigned/in_progress）
③ 驗證 vendor 綁定（linked_company_id + auto_dispatch + partner_routing_template_id）
④ 在對方公司 upsert「祥興印刷」為客戶（is_internal_partner=true）
⑤ 產生對方公司的工單編號（next_doc_no）
⑥ 在對方公司建立工單（status=confirmed）
⑦ 展開對方工序（reuse expand_order_tasks）
⑧ 建立 cross_company_link（status=dispatched）
⑨ 回填 orders.source_link_id
⑩ 更新發包方工序 → outsourced
⑪ 寫事件日誌
```

### RPC 函式簽章

| 函式 | 參數 | 誰可呼叫 | 說明 |
|------|------|----------|------|
| `dispatch_outsource(uuid, uuid, numeric, date?, text?)` | task_id, vendor_id, amount, due_date, note | manager/owner | 發包外包，自動在對方公司建單 |
| `complete_outsource(uuid)` | link_id | trigger（自動） | 完工回寫，產生雙邊應付/應收 |
| `reject_outsource(uuid, text?)` | link_id, reason | 對方 manager/owner | 拒接外包，退回發包方工序 |
| `cancel_outsource(uuid, text?)` | link_id, reason | 發包方 manager/owner | 取消發包，退回工序 |

所有函式回傳 `jsonb`，格式：`{ ok: true, ... }`

### 設計決策：RPC vs Edge Function

SA-SD 原定用 Edge Function + service_role key 實現跨公司寫入。實作改為 **security definer RPC**，因為：
- security definer 以函式擁有者（postgres 超級用戶）身份執行，**等效於 service_role**，可繞過 RLS 寫入對方公司資料
- 不需要額外部署 Edge Function，降低維護成本
- 前端呼叫方式從 `supabase.functions.invoke()` 改為 `supabase.rpc()`，更簡單
- 安全性相同：驗證邏輯都在函式內部，前端無法繞過

    auto_dispatch = true,
    partner_routing_template_id = '<沂融的範本ID>'

  and name = '沂融企業社';
